# Agentic SfM — Complete Codebase & Research Context

## Project Goal

Train a Multimodal LLM (Qwen3-VL-8B-Instruct) via RL (GRPO/DAPO) to act as an agent that orchestrates vision tools (crop, match, doppelganger_check) to improve image matching on hard, low-overlap pairs from MegaDepth-1500.

## Architecture (3-GPU on AIRE L40S)

```
GPU 0: vLLM rollout server (Qwen3-VL-8B, fast sampling)
GPU 1: LoRA training model (policy gradient updates)
GPU 2: Tool server (LoFTR/MASt3R matching, crop, SfM)
```

## Research Context (Key Papers)

- **DAPO** (arXiv:2503.14476) — Decoupled Clip + Dynamic Sampling: clip_high=0.28 prevents entropy collapse, dynamic sampling skips zero-variance groups, token-level loss for long-CoT
- **Visual-ARFT** (arXiv:2505.14246) — GRPO for multimodal agentic tool use (search + coding), verifiable rewards, +18.6% F1 over baseline, surpasses GPT-4o
- **ToolRL** (arXiv:2504.13958) — systematic reward design for tool-integrated reasoning: fine-grained decomposition > coarse, dynamic reward scaling, +17% over base, +15% over SFT
- **RC-GRPO** (arXiv:2602.03025) — reward-conditioned rollouts to prevent group variance collapse after SFT peakedness
- **Off-policy GRPO** (arXiv:2505.22257) — sample reuse for μ iterations to reduce vLLM serving cost

## verl Agent Loop — What It Is

**Agent Loop** (added in verl v0.4.2, status: alpha) is the general interface for **multi-turn rollout and agentic RL**. It's designed so you can plug in a custom agent loop that calls LLMs, tools, and environments during rollout, then use the trajectory for PPO/GRPO training.

### Architecture

The key components are:

- **`AgentLoopBase`** — Abstract base class. You implement `async def run(sampling_params, **kwargs) -> AgentLoopOutput`. This is what our [AgenticSfmAgentLoop](file:///scratch/kcwp264/agentic-sfm/src/agentic_sfm/verl_agent_loop.py:102:0-374:52) in `@/scratch/kcwp264/agentic-sfm/src/agentic_sfm/verl_agent_loop.py` extends.
- **`AgentLoopOutput`** — Returns `prompt_ids`, `response_ids`, and `response_mask` (1 for LLM tokens, 0 for tool response tokens). This is critical for RL: the mask ensures PPO only updates on LLM-generated tokens, not tool observations.
- **`AgentLoopManager`** — Orchestrates workers, syncs vLLM weights with FSDP before rollout (`wake_up`), and offloads after (`sleep`).
- **`AgentLoopWorker`** — Runs each prompt's agent loop coroutine in parallel.
- **`LLMServerClient`** — Proxy to vLLM/SGLang async servers with load balancing and sticky sessions per request.

### PPO Step Flow

1. PPOTrainer samples batch → calls `AgentLoopManager.generate_sequences`
2. Manager `wake_up` all LLM servers (sync FSDP weights → vLLM)
3. Splits batch → sends to `AgentLoopWorker`s
4. Each worker spawns [AgentLoopBase.run()](file:///scratch/kcwp264/agentic-sfm/src/agentic_sfm/verl_agent_loop.py:144:4-317:9) per prompt — calls LLM generate, executes tools, appends observations, loops until done
5. Manager gathers results → returns to PPOTrainer for training
6. Manager `sleep` all servers (free KV cache, offload weights to CPU)

### Registration

Custom agent loops are registered via a YAML config file (`agent_loop_config_path`), which verl loads via `OmegaConf` and `hydra.utils.instantiate`. This is exactly what our `agent_loop.yaml` does — it points to [agentic_sfm.AgenticSfmAgentLoop](file:///scratch/kcwp264/agentic-sfm/src/agentic_sfm/verl_agent_loop.py:102:0-374:52).

### Key Design Decisions from Docs

- **Token-level API, not chat completion**: verl uses token IDs directly (not text) to avoid irreversible token↔text conversion issues. This is why our `AgentLoopOutput` returns `prompt_ids` and `response_ids` as token lists.
- **`response_mask` is critical**: 1 for LLM tokens, 0 for tool observations. PPO only computes loss on masked=1 tokens.
- **`enable_sleep_mode`**: vLLM servers can sleep between rollout phases, freeing GPU memory for FSDP training. This is the key mechanism for co-locating vLLM and FSDP on the same GPU.
- **Reward is computed after [run()](file:///scratch/kcwp264/agentic-sfm/src/agentic_sfm/verl_agent_loop.py:144:4-317:9)**: The custom reward function (`pkg://agentic_sfm.verl_reward`) receives the final `AgentLoopOutput` and computes reward from match quality + pose accuracy.

### What Our Implementation Does

Our [AgenticSfmAgentLoop](file:///scratch/kcwp264/agentic-sfm/src/agentic_sfm/verl_agent_loop.py:102:0-374:52) at `@/scratch/kcwp264/agentic-sfm/src/agentic_sfm/verl_agent_loop.py`:
1. Receives image pair prompt + ground-truth pose
2. Registers images with the tool server (MASt3R/LoFTR)
3. Calls vLLM to generate assistant response → parses tool call
4. Executes tool ([match](file:///scratch/kcwp264/agentic-sfm/tools_server/server.py:472:0-474:74), [crop](file:///scratch/kcwp264/agentic-sfm/tools_server/server.py:467:0-469:44), `crop_and_match`, etc.) via HTTP to tool server
5. Formats observation → appends to conversation
6. Loops until model emits `{"tool": "done"}` or max turns
7. Computes reward from final match result vs ground-truth pose

1. **Use 2 GPUs** (TP=2 for vLLM, or DP=1 + FSDP sharding across 2) — this is the supported configuration
